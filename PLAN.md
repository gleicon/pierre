## Roadmap

### Walking skeleton
- [x] `pierre.toml` parses minimal config (data dir, native listen addr, field allowlist — tier/flush/bucket settings deferred to their respective phases)
- [x] `storage` wraps edgestore behind `Arc<RwLock<Engine>>` via `edgestore-tokio`'s existing `AsyncEngine`, single-writer lock enforced
- [x] `storage` encodes keys with a time prefix so range scans map to time ranges — trailing 8 bytes are fresh per-record randomness (UUIDv7-inspired, nanosecond precision kept instead of UUIDv7's millisecond field), not a monotonic counter that reset to 0 on every restart and risked colliding across process lifetimes (`tests/key_collision.rs`, DECISIONS.md)
- [x] `ingest` defines the normalized `Record` type
- [x] Native binary protocol listener parses into `Record` and commits through `ingest`
- [x] Ingest path extracts configured typed fields synchronously before ack
- [x] Ingest path computes Drain-style `template_id` synchronously before ack (masking-based simplification, not a full Drain prefix tree — revisit if template clustering quality matters later)
- [x] `query` answers selector + time-range reads against `storage`
- [x] End-to-end: a native-protocol write is durable (WAL) and immediately readable by selector/time-range query — proven by integration test and a real running binary hit over TCP

### Loki compatibility
- [x] Loki push API listener parses into the same `Record` type — stream labels become fields (allowlist-filtered, same as native), values decode to `WireRecord`s via the shared `ingest::commit` path
- [x] **Real collector interop — verified against an actual Promtail container**, not just a synthetic wire-format-matching push (`tests/e2e/run_promtail_e2e.sh`, Docker). This surfaced two real, previously-unknown bugs, both fixed:
  - **Pierre's push endpoint only accepted JSON; real collectors default to protobuf+raw-snappy.** Promtail's first real push attempt got a 415 on every batch. Real Loki's actual wire format is a `PushRequest` protobuf message (`pkg/push/push.proto`, fetched from upstream for exact field-number compatibility), raw-snappy-compressed (not framed) — confirmed against Loki's own server source (`pkg/loghttp/push/push.go`: "no content-type header, or `application/x-protobuf`: expect snappy compression"). Fixed: `push_handler` now dispatches on Content-Type — JSON only when explicitly declared, protobuf+snappy otherwise (matching Loki's own default-to-protobuf behavior). New `src/lokiproto.rs` (prost-generated from `proto/logproto.proto`) plus `logql::parse_label_set` reused for the wire format's `{k="v"}`-style label-set string.
  - **`textindex::search()`/`GET /query/search` could hang the server on a wide time range.** `bucket_namespaces_for_range` enumerates every bucket *index* between `start`/`end`, not just ones with data; `start=0, end=i64::MAX` — a plausible thing for a client or this project's own e2e test to try — enumerates ~2.56 million buckets, each a real async round-trip. Fixed with an upfront analytical bucket-count check (`MAX_BUCKETS_PER_SEARCH = 200`) that rejects (400, not a hang or 500) before ever entering the loop.
  - End-to-end proof: a real `grafana/promtail:latest` container reads a 50-line synthetic JSON log file, promotes `level` to a Loki label via `pipeline_stages`, ships via real protobuf+snappy to Pierre's real running binary; verified all 50 lines land with correct content via both `/query/search` (BM25, all 50 unique sequence markers present, none missing/duplicated) and `/loki/api/v1/query_range`.
- [x] `GET /loki/api/v1/query_range` — deliberate LogQL subset (`{label="value"} |= "text"`), matches real Loki's response shape (`status`/`data.resultType`/`data.result[].stream|values`) so Grafana's Loki datasource can parse it. Verified via integration test and a real curl against the running binary.

### Rollups
- [x] Rollup consumer drains a bounded channel fed from ingest without blocking writes
- [x] Channel-full drops a contribution and increments a counter instead of blocking (proven: 5000 sends against a 1024-capacity channel with a stalled consumer, all dropped/counted, ingest never blocks)
- [x] Exact-counter rollup updates live minute buckets and flushes on minute boundaries (bucket duration configurable — 60s in prod, shortened in tests)
- [x] Minute buckets merge into hour/day/month tiers algebraically (no raw rescans) — one `merge_up` function reused for minute→hour, hour→day, day→month, each on its own wall-clock timer; test proves hour tier sums two persisted minute buckets (2+0 → total 2), never re-touching raw log lines. Day/month merges share the identical code path, only the minute→hour case has a dedicated test.
- [x] HyperLogLog rollup kind supported — `FieldSketch` enum (Exact/Hll) with a fixed-seed hasher (`DefaultHasher`, not `RandomState` — needed for merge/cross-restart determinism) and a real `merge()` from `hyperloglogplus`; self-describing tag-byte serialization so the generic `merge_up` doesn't need external config to know a bucket's kind
- [x] Top-K (Space-Saving/CMS) rollup kind supported — Space-Saving implemented directly (no crate, per SPEC.md constraints), bounded-capacity map with min-eviction; test proves a true heavy hitter (200 hits) survives 50 one-off noise keys at capacity 20
- [x] DDSketch rollup kind supported — `sketches-ddsketch` (relative_accuracy=0.01, matching the PRD's example), real `merge()`, non-numeric values logged and dropped rather than panicking the worker; test proves p99 of 1..=1000 estimates within ~1% before *and* after a merge across two sketches
- [x] Rollup tiers persist with independent TTLs via write-time cohorting (added `put_with_ttl` to `edgestore-tokio`'s `AsyncEngine`, which didn't wrap it yet)
- [x] Rollup definitions are declared in `pierre.toml` with no code changes required to add one — `[[rollup]]` tables with `field`/`kind`, generic over any `RollupKind` (proven by adding `trace_id`/`hll` alongside the existing `exact` fields with zero code changes)
- [x] Aggregation queries are served from merged sketches only, never raw rescans — `aggregate::merged_sketch` picks exactly one rollup tier by query span (avoids double-counting a tier against its own already-merged parent) and merges that tier's buckets; exposed via `GET /query/aggregate`. Real finding along the way: rollup buckets key by **wall-clock processing time**, not the ingested record's own `timestamp_ns` — an aggregation query window must bracket real "now", not a record's (possibly backfilled/historical) timestamp. Worth knowing for delayed/batched ingestion.

### Full-text search
- [x] BM25 indexing runs off the synchronous ingest path via its own bounded channel — required adding `index_text`/`search_text`/`search_text_with_options`/`delete_text` wrappers to `edgestore-tokio`'s `AsyncEngine`, which didn't wrap `TextEngine` at all (same gap pattern as `put_with_ttl`/`flush_to_segments`/`export_manifest` before it)
- [x] BM25 index boundaries align to time-buckets (bounded in-memory index size) — one namespace per bucket window (`text_bucket_{start_ns}`), configurable duration
- [x] Line-filter queries dispatch to the relevant time-bucket index(es) and merge results across buckets — `textindex::search()`, tested across a 2-bucket span with results merged by score
- [x] Periodic `flush()` timer persists BM25 indexes on a bounded interval (reuses `Storage::flush()`, same fix as `backup`'s immediate-first-tick gotcha applied here too)
- [x] Crash-then-restart leaves BM25 search complete (no permanently unsearchable documents) — real crash simulation: index doc1, flush, index doc2 (never flushed), abort the worker task and drop the last `Arc<Storage>` reference (not just a graceful shutdown), reopen fresh. Both documents searchable, including the one that was only ever in-memory at crash time — proves Pierre's own textindex module doesn't defeat edgestore's self-healing rebuild, not just that edgestore's rebuild works in isolation

### Tiering & retention
- [x] Object-storage decision made, corrected, then upgraded to real tiering — edgestore 1.1.0's `edgestore-tier`/`TieredEngine` shipped real point-lookup read-through (verified against LocalStack S3, not just filesystem); `AsyncTieredEngine` (async wrapper, `edgestore-tokio`, feature `tier`) built and fully tested, including a Pierre-specific `fetch_archived_overlapping()` for range-aware selective rehydration (proven to fetch only the overlapping segment, not the whole archive)
- [x] `Storage` migrated from `AsyncEngine` to `AsyncTieredEngine` — `Storage::open(dir)` keeps its exact old signature (defaults to a local-disk archive under `{data_dir}/_archive`, so every existing test needed zero changes); `Storage::open_with_remote(dir, remote)` added for explicit S3 config
- [x] Hot→warm aging moves data from memtable to local BM25-indexed segments on policy — periodic `flush_to_segments()`, interval now configurable (`hot_to_warm_flush_interval_secs`), not hardcoded
- [x] Warm-segment archival via `TieredEngine::archive_segments`, config-selectable between `FilesystemRemoteStore` and `S3RemoteStore` — verified both for real: filesystem via a local test, S3 against a live LocalStack container (upload confirmed by an independent download-and-compare, not just "worker ran without erroring")
- [x] Archived-segment metadata persists across restarts via a plain sidecar file (`archived_segments.json`, sibling to the segment files) — **not** through the KV engine itself. Found and fixed a real bug here: an earlier version persisted this bookkeeping via `storage.put_with_ttl`, which created a self-perpetuating feedback loop (bookkeeping write → next flush turns it into a new segment → archive pass archives that segment → writes more bookkeeping about it → forever, even at zero real ingest). Caught via an actual multi-tick test run (5 segments from 1 ingested record), not code review. Fixed by moving persistence outside the engine entirely; re-verified stable at exactly 1 segment / 1 archived entry across repeated ticks with no new data.
- [x] Queries are served entirely from local segments for range/prefix; `RemoteStore` is never read on that path (true by construction — `TieredEngine`'s own design, only `get()` reads through)
- [x] Expired data is removed via deathtime-cohort compaction without rewriting live neighbors — real test through Pierre's own `Storage.compact_once()`: a 1-second-TTL record's cohort is removed while a 100-second-TTL neighbor in a different cohort survives untouched. Required adding `compact_once`/`Storage::open_with_options` (custom `cohort_window_secs` — previously hardcoded to edgestore's 1-hour default with no override).
- [x] **ImmutableEngine-based ephemeral cold-range queries — built, not just deferred anymore.** `Storage::query_archived_range()`: downloads only the archived segments overlapping a query's time range, builds a throwaway `edgestore::ImmutableEngine`, queries it, discards it. Verified with a `Storage` instance holding **zero local data of its own** — correct results, and `.dat` file count in that instance's directory is identical before/after the query (asserted, not assumed). Required two small additions to `edgestore-tier`/`edgestore-tokio`: `TieredEngine::download_segment` (byte fetch without importing — `fetch_segment` always imports, which isn't what an ephemeral view needs) and its async wrapper.

**Bugs found and fixed in edgestore-repl's `S3RemoteStore` across this work (SPEC.md #L5, resolved upstream in 1.1.0):**
1. `S3RemoteStore::new()` called `Runtime::block_on()` directly in its constructor — panicked from async context (which `main()` always is).
2. `S3RemoteStore` owned an `Arc<Runtime>` unconditionally; dropping it from async context panicked too.
Both fixed upstream (`owned_runtime: Option<Arc<Runtime>>`, `None` when reusing an ambient handle) — verified in code and by re-running the LocalStack test with Pierre's `mem::forget` leak workaround removed (still passes, workaround deleted).

### Auth and local retention (from the `/ds-grill-me` session, see DECISIONS.md)
- [x] Static bearer-token auth — `Authorization: Bearer <token>` checked against a configured list, one shared axum middleware (`src/auth.rs`) applied to all three HTTP surfaces (Loki push, Loki query_range, native query API). Empty list (default) means auth is off entirely. Native TCP ingest protocol stays unauthenticated (no existing client convention to match). Verified via `tests/auth.rs` (missing/wrong/correct token, both routers) and a real running-binary smoke test (401/401/200).
- [x] `pierre::retention` — a small, shared `is_due(event_time, grace_period)` predicate, not a unified scheduler; deliberately doesn't merge the three existing worker loops.
- [x] Local segment pruning — after archiving, once `local_retention_secs` has elapsed (opt-in, `None`/unset by default), `backup::spawn`'s existing worker deletes the local segment's files via a new `Engine::prune_local_segment`/`TieredEngine::prune_local_segment`/`AsyncTieredEngine::prune_local_segment` chain (added this round, mirroring the existing `replace_segment`/`strip_text_index` pattern already in edgestore). Archived-segment bookkeeping now tracks an explicit `archived_at` timestamp per segment (`ArchivedSegmentRecord`, `backup/mod.rs`) since edgestore's `SegmentMeta` has none. Verified end-to-end (`tests/local_pruning.rs`): segment flushed → archived → confirmed still present locally before the grace period → confirmed deleted after → confirmed still queryable via archived read-through. This is what makes tiering actually reclaim local disk; before this, Pierre archived forever without ever pruning.
- [x] Pierre's bespoke `query_archived_range`/`logs_key_bounds` deleted — superseded by edgestore 1.1.4's built-in `range()`/`prefix()` read-through (verified empirically, see `tests/archived_range_readthrough.rs`, which pins the behavior against regression and is what local pruning's safety now depends on).
- [~] `strip_text_index_after_archive` — wired end-to-end (`Storage::open_with_options` → new `AsyncTieredEngine::open_with_options` → `TieredEngine::with_text_stripping`), segment-level rewrite confirmed correct. **Known upstream gap, found by testing (`tests/text_index_stripping.rs`), not assumed:** not durable across a restart — edgestore's WAL rotation is size-based (64MB), unrelated to flush/strip events, so the original WAL entry for a stripped write usually survives and gets replayed back into the memtable on reopen, silently undoing the strip. Defaults to `false`, documented loudly in `pierre.toml`/`config.rs`; not recommended until the upstream WAL/strip interaction is fixed.

### Pre-launch decisions & measurements (blocking, from SPEC.md Known Limitations)
- [x] BM25 crash-recovery rebuild cost benchmarked at 10K/100K/1M records — #L2, **fully resolved: root cause found and fixed, not just mitigated.** Original finding: indexing throughput within one still-open bucket collapsed from ~13,000 docs/sec (10K docs) to ~750 docs/sec (100K docs), an ~18x degradation; reopen/rebuild time itself was always fast (never the bottleneck). Traced the actual cause: `Engine::index_text` unconditionally called `remove_document` (an O(total index size) scan) before every `add_document`, even for documents never seen before — pure waste for Pierre's unique-key log workload, turning indexing into O(n²) total work. Fixed upstream with a capacity-adaptive Bloom filter existence check (`edgestore/src/text/bloom.rs`) — first attempt used a fixed capacity that degraded silently and just as badly once exceeded (45.77x slowdown found at 1.5x over its designed capacity), corrected to double capacity on saturation (amortized O(1), same analysis as `Vec::push`). **Measured result:** 10K → ~5-6x faster; 100K → ~73-90x faster; 1M docs — previously never completed in any run (killed after 30-40+ min) — now **18.48s clean/isolated**, completely flat throughput, no degradation at any scale tested. New diagnostic tools kept as permanent examples: `examples/bench_index_text_breakdown.rs` (front-vs-back throughput ratio), `examples/bench_index_text_progress.rs` (checkpoint-by-checkpoint progress, used to distinguish a real stall from system CPU contention). The `textindex_bucket_duration_secs` 300s default is no longer load-bearing for *this* reason specifically, though it still has independent justifications (rebuild time, memory footprint, query merge cost) — a candidate to revisit, not reverted reflexively.
- [x] End-to-end ingest throughput benchmarked (HTTP → WAL → ack) — #L3, resolved. `examples/bench_ingest_throughput.rs`: 50 concurrent native-protocol connections, 5s sustained → **34,490 req/s achieved**, clearing the 10,000 req/s NFR-2 target with real margin, not a hypothesis anymore.
- [x] LocalStack S3 performance and consistency, measured for real (`examples/bench_s3_localstack.rs`): archive (upload) 3K–210K records/sec depending on segment size; cold-query (download + ephemeral `ImmutableEngine`) 15K–414K records/sec; 20 concurrent upload/download round-trips, 0 failures/mismatches.
